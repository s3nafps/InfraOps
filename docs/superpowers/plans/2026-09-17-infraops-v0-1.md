# InfraOps v0.1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Deliver a reproducible v0.1 InfraOps installation whose CLI/web onboarding leads to a safe, tested incident investigation and remediation flow with structured actions, human approval, verification, and audit history.

**Architecture:** Build the Python FastAPI control plane and PostgreSQL domain model first, then add the durable worker, deterministic demo host/provider, Rust protocol/agent/CLI, and Next.js dashboard around the same contracts. The demo lab is the first real vertical slice; SSH, remote agent deployment, and optional model providers plug into the same `HostAdapter` and provider interfaces without changing workflow code.

**Tech Stack:** Python 3.12+, FastAPI, Pydantic v2, SQLAlchemy 2, Alembic, PostgreSQL 16, Redis 7 Streams, Rust stable, Tokio, Serde, Axum/WebSocket client, Clap, Next.js App Router, React, TypeScript, Vitest, Testing Library, Playwright, Docker Compose v2, GitHub Actions.

**Spec:** `docs/superpowers/specs/2026-09-17-infraops-design.md`

## Global Constraints

- PostgreSQL is the source of truth for workflow state, approvals, action records, and audit events; Redis is a delivery mechanism, never the only copy of a security-relevant event.
- Model output is untrusted data and may request only versioned structured tools; no model, browser, API caller, or CLI command may submit arbitrary shell text.
- The official deployment is Docker Compose and must work on one workstation, VM, or VPS; Kubernetes is not required for v0.1.
- The default Compose profile binds the reverse proxy, including the agent session route, to localhost; PostgreSQL and Redis are never published.
- Provider authentication uses only documented provider methods; no private or reverse-engineered OAuth flow is permitted.
- Mutating and high-risk actions require approval; forbidden actions always fail closed.
- Credentials, private keys, tokens, and master keys are never placed in prompts, evidence, API responses, audit payloads, or committed files.
- Every new behavior follows red-green-refactor: write one focused failing test, run it and observe the expected failure, implement the smallest passing change, run the full relevant suite, then commit.
- CI must not require production hosts or real provider credentials.
- Use semantic versioning and label synthetic lab evidence as synthetic.

```python
# services/control-plane/src/infraops_control/contracts.py
from enum import StrEnum
from uuid import UUID
from pydantic import BaseModel, ConfigDict, Field


class RiskClass(StrEnum):
    READ_ONLY = "READ_ONLY"
    LOW_RISK = "LOW_RISK"
    MUTATING = "MUTATING"
    HIGH_RISK = "HIGH_RISK"
    FORBIDDEN = "FORBIDDEN"


class IncidentState(StrEnum):
    INCIDENT_CREATED = "INCIDENT_CREATED"
    TRIAGE = "TRIAGE"
    COLLECT_EVIDENCE = "COLLECT_EVIDENCE"
    ANALYZE = "ANALYZE"
    PROPOSE_REMEDIATION = "PROPOSE_REMEDIATION"
    WAITING_FOR_APPROVAL = "WAITING_FOR_APPROVAL"
    EXECUTE = "EXECUTE"
    VERIFY = "VERIFY"
    RESOLVED = "RESOLVED"
    ESCALATED = "ESCALATED"


class ActionRequest(BaseModel):
    model_config = ConfigDict(extra="forbid")
    action: str
    host_id: UUID
    target: dict[str, str] = Field(min_length=1)
    reason: str = Field(min_length=1, max_length=1000)
    idempotency_key: str = Field(min_length=16, max_length=128)
    risk_class: RiskClass | None = None
    action_hash: str | None = None
```

Add equivalent strict models for `EvidenceItem`, `ExecutionResult`, and `AuditEvent`; keep wire JSON names identical to the schemas.
